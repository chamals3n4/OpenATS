# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

OpenATS is a self-hosted applicant tracking system. It is a **pnpm workspace**: `backend/` and `frontend/` are separate packages sharing one root `package.json` and one root `pnpm-lock.yaml`. Run `pnpm install` once at the root, and use the root scripts (`pnpm dev`, `pnpm build`, `pnpm test`) or `pnpm --filter ./backend <script>` to target one package.

## Commands

### Backend (`backend/`)

```bash
pnpm dev              # nodemon + tsx, port 8080
pnpm build            # tsc → dist/
pnpm start            # node dist/src/server.js
pnpm test             # vitest (watch mode)
pnpm test:run         # vitest (single run)
pnpm vitest run tests/unit/object.util.test.ts                 # run one test file
pnpm drizzle-kit generate   # generate migration SQL (always commit output)
pnpm drizzle-kit migrate    # apply migrations to DB
pnpm tsx src/db/seed.ts     # seed pipeline stages (required on first setup)
pnpm tsx src/db/backfill-scores.ts   # re-score every candidate (run after changing how scores are calculated)
pnpm tsx src/db/backfill-cv-text.ts  # queue every CV whose text has not been read yet (the worker must be running)
pnpm tsx src/db/backfill-cv-text.ts --reparse   # work out sections, years of experience and education again from stored CV text (no worker, no files)
pnpm tsx src/db/move-resumes-to-private-bucket.ts   # one-off when upgrading from v0.6.0: move CVs out of the public bucket
pnpm tsx src/db/sanitize-job-descriptions.ts   # one-off when upgrading from v0.6.0: clean job descriptions saved before they were sanitized
docker compose up -d        # local Postgres (5432) + Redis (6379), see docker-compose.yml at the repo root
```

### Frontend (`frontend/`)

```bash
pnpm dev      # next dev --turbo, port 3000
pnpm build    # next build
pnpm lint     # eslint
pnpm exec tsx scripts/create-admin.ts   # create or reset a super admin (also `make admin` at the root)
```

## Architecture

### Backend

- **Express 5** (not 4) with TypeScript compiled to CommonJS (`"module": "commonjs"` in tsconfig). `tsx` handles dev transpilation.
- **Feature-first layout**: code is organized by feature under `backend/src/modules/<feature>/`, each holding that feature's `*.controller.ts`, `*.service.ts`, and `*.routes.ts` together (e.g. `modules/candidate/candidate.controller.ts`). There are no top-level `controllers/`, `services/`, or per-feature `routes/` directories — put new feature code in its module, not in a layer folder.
- **Request flow**: `backend/src/server.ts` → `backend/src/app.ts` → `backend/src/routes/index.ts` → each module's routes file → that module's controller → service.
- **Shared code**: `backend/src/shared/auth/verify-token.ts` is the single JWT verification path (tokens are issued by Better Auth in the Next.js server and verified against `AUTH_JWKS_URL`), used by both `auth.middleware.ts` and the Socket.IO handshake so the two transports cannot drift on who counts as authenticated; `backend/src/shared/services/` holds services used by 2+ modules (`mail`, `socket`, `r2`); `backend/src/shared/integrations/` holds external-provider infra (`connection.service`, `registry`, `crypto`, `google-meet.provider`) — distinct from the `modules/integrations/` feature, which is CRUD for a company's configured integrations. Cross-module imports (e.g. `offer` → `../template/template-engine.service`) are fine; only promote to `shared/` when 2+ unrelated modules need it.
- `backend/src/routes/` keeps only `index.ts` (mounts every module router) and `public.routes.ts` (cross-cutting `/public/*` aggregator that spans several modules). `modules/job/job.routes.ts` also mounts the `pipeline`, `hiring-team`, and `custom-question` modules as sub-routes under `/jobs`.
- Imports are plain relative paths (no `@/` alias — `module: commonjs` + `moduleResolution: node` would emit unresolvable `require("@/…")` into `dist/`). Depth stays at `../../` at most.
- **Auth middleware** (`backend/src/middlewares/auth.middleware.ts`): verifies OpenATS-issued JWTs through `verify-token.ts`. The token's `sub` is the `users.id`; role (`super_admin`, `hiring_manager`, `interviewer`), `is_active` and `banned` are read from the row on every request, so changes apply immediately. Users are never provisioned from a token — an unknown id is a 401.
- **Public routes** (`/public/*`) have no auth middleware. `checkOrigins` applies the company's allowed-origins list (`isOriginAllowed` in `modules/settings/page-settings.service.ts`, shared with the CORS callback in `app.ts`): an empty list allows everything, and `FRONTEND_URL` is always allowed so the built-in careers page cannot be locked out. It only stops other sites embedding the API and is **not** access control (a request with no Origin passes), so nothing private may sit behind it. The list is cached in memory for 30 seconds and cleared when the setting is saved. Assessment endpoints (`/public/assessment/:token`) use token-based auth.
- **`trust proxy`** is set in `app.ts` from `TRUST_PROXY` (`parseTrustProxy` in `config/env.ts`; default 1 hop, `false` for none, `true` refused), so `req.ip` is the visitor and not the proxy. Every IP-keyed limiter depends on it.
- **Rate limiting**: `/public/*` has its own IP-keyed limiters in `public.routes.ts`. The authenticated API is limited by `middlewares/rate-limit.middleware.ts`, keyed by **user id** rather than IP so one office behind a NAT does not share a budget — `apiLimiter` is mounted on all of `/api`, and `expensiveLimiter` on uploads. Both are tunable with `RATE_LIMIT_API` / `RATE_LIMIT_EXPENSIVE`.
- **Job descriptions** are the one place HTML written by a user is put into a page. `sanitizeJobDescription` (`modules/job/job-description.ts`, `sanitize-html`) cleans them to what the editor produces, in `job.service` on create and update and again in the public job response; the dashboard cleans once more with `cleanRichText` (`frontend/lib/clean-html.ts`, DOMPurify) before `dangerouslySetInnerHTML`. Keep the two tag lists the same. The careers page is rendered on the server, where DOMPurify cannot run, so it relies on the API's output. Any new stored HTML must be cleaned the same way or shown with `SandboxedHtmlPreview`, as offer letters and email previews are.
- **Application answers** are checked on the server in `modules/candidate/application-answers.ts` (`findAnswerProblem`, pure) before anything is saved: every question that must be answered is, each option belongs to its question, and each question belongs to the job. A question with a knockout option must always be answered (`mustAnswer`), required or not, and `/public/jobs/:jobId/questions` reports it as required without exposing the knockout flag.
- **Assessments** have two sets of routes. The hiring team's (`modules/assessment-execution/assessment-execution.routes.ts`, under `/api`) each check `canViewCandidate`, because answers and scores belong to one candidate. The candidate's own (`/public/assessment/:token` in `routes/public.routes.ts`) are limited per link, with a larger budget for saving answers than for starting and submitting. The time limit (`assessments.time_limit`, in **minutes**) is enforced by the server in `isPastDeadline`, not only by the clock in the browser. `completeAttempt` locks the attempt row, so a double submit completes and emails once; `completeAbandonedAttempts` (periodic check in `server.ts`) finishes and grades attempts that were started and left.
- **Per-job authorization** has two rules, both in `shared/auth/job-access.ts`. **Seeing a job and its candidates** (`canViewJob`, `canViewCandidate`; middleware `requireJobView`, `requireCandidateView`): super admins and hiring managers see every job, interviewers only the jobs they are on the hiring team of. Hiring managers being company-wide is deliberate; do not scope them to their own jobs. Use this rule for anything about a candidate or a job (page, CV, emails, ratings, assessments, interviews, rejections, and a job's pipeline, team, scorecard and questions). For one interview use `canViewInterview` / `requireInterviewView`, which also passes the interviewer the interview is assigned to, because any user can be picked to interview without being on the team; `interviewService.getAll` applies the same rule to the list. **Offers are managers only**: `offer.routes.ts` mounts `requireManager` on the whole router. A new route that returns candidate or job data must carry one of these guards; being signed in is not enough. **Being in the team chat** (`canAccessJob`, `canAccessCandidate`; middleware `requireJobAccess`, `requireCandidateAccess`): hiring-team members and super admins only, the same rule the sockets use. Job creation adds the creator to the hiring team.
- **`req.user`** is available via augmentation in `backend/src/types/express.d.ts`.
- **Socket.IO** runs on the same HTTP server. Connections require a valid OpenATS-issued JWT in `handshake.auth.token`, verified by an `io.use()` middleware before any handler runs; the verified user is on `socket.data.user`. Chat handlers take the sender from that user, never from the client payload. Dashboard-wide events are emitted to the `staff` room (which every authenticated socket joins), not with a bare `io.emit()`. CORS is restricted to `FRONTEND_URL`.
- **Socket authorization** is separate from authentication: `join_job` / `join_candidate` are gated by `shared/auth/job-access.ts` (hiring-team membership, with `super_admin` exempt), and the chat write handlers require the socket to already be in that room — so a client cannot skip the join and write to an arbitrary job. Client sockets are created by `frontend/lib/socket.ts`, which re-fetches a token from `/api/socket-token` on every connect attempt so reconnects survive token expiry.
- **Emails to candidates** all go through `sendCandidateEmail` in `shared/services/candidate-mailer.ts`, which sends and then writes the result (sent or failed) to `email_messages`, the candidate's email history. It never throws; the caller decides whether a failed email fails the action. The built-in emails are built in `shared/services/candidate-emails.ts` (pure functions, values escaped there). Their subject and message are editable per company: the defaults and the variables each one allows are in `shared/services/system-emails.ts`, a company's own wording is a row in `system_email_templates` (no row means the default, so deleting the row resets it), and callers load it with `emailContext(purpose)`. The heading, details table and buttons are added in code and are not editable, so a required link cannot be removed, and every email uses the one layout in `shared/services/email-layout.ts`. `mail.service.ts` is only the Resend transport. Send after the database change is committed, never inside a transaction.
- **Interview times cannot overlap** for one interviewer. The database enforces it with the `candidate_interviews_no_overlap` exclusion constraint (in `drizzle/0042_*.sql`, not in the Drizzle schema, which cannot express one): scheduled interviews of the same interviewer, each taking `duration_minutes` (60 when null). `modules/interview/interview-slots.ts` has the same rule for showing slots as taken (`overlapsBusy`) and `isInterviewClash` to turn the constraint error into a 409 `SLOT_TAKEN`; any new code that sets `scheduled_at` must catch it.
- **Dates and times in emails** are formatted in the company's time zone (`company.time_zone`, an IANA name, default UTC) with `formatEmailDate` / `formatEmailTime` in `shared/services/time-zone.ts`. `emailContext()` supplies `timeZone`; never call `toLocaleDateString` for an email without it.
- **Offers** change status only through `offerRepository.transition`, a conditional update, so two answers at once cannot both apply. An accepted, declined or expired offer cannot be edited (`OfferClosedError`, 409). `expires_at` is optional; the periodic check in `server.ts` expires overdue offers, and accept/decline refuse after it. Loading the public offer never marks it viewed: the page calls `POST /public/offers/:token/viewed` once it is on screen, because email scanners fetch links.
- **Interview calendar entries**: an interview gets at most one, made in `modules/interview/interview-confirm.ts` (`completeInterviewBooking`) when it gets its time. It goes in the interviewer's own Google Calendar when they have connected Google (per-user OAuth, `shared/integrations/`), with a Meet link only if one was asked for. An interviewer who has not connected gets no entry. There is no shared or company-wide calendar; do not add a second place to write events.
- Logger is winston with console transport only (file transports commented out).
- `exactOptionalPropertyTypes: false` in tsconfig — deliberate.
- **Redis + BullMQ**: CV analysis runs as a background job queue, colocated under `backend/src/queues/cv-analysis/` (`queue.ts`, `worker.ts`, `events.ts`); shared Redis connection factory is `backend/src/config/redis.ts`. Connection is read from `REDIS_URL` (defaults to `redis://localhost:6379`). A dedicated connection is created per Queue/Worker (BullMQ best practice), not a shared singleton.
- **CV text** is read from every uploaded CV on this server, with no AI and no outside service, and stored in `candidate_cv_text` (one row per candidate, with a generated `search_vector` for full-text search). `requestCvExtraction` in `queues/cv-extract/queue.ts` is called wherever a CV arrives or is replaced; the worker runs in the same process as the CV analysis worker (`src/worker.ts`). That process is the **background worker and is required**: `queues/worker-status.ts` (`getWorkerStatus`) reports whether one is connected, to `/health`, to `GET /settings/worker`, and so to the warning in Settings and on a waiting CV. The queue worker reads each file with `extractCvTextWithTimeout` (`cv-text/extract-with-timeout.ts`): on its own `worker_threads` thread with a 30 second limit, after which the thread is terminated and the CV is `UnreadableCvError` (not retried), so one PDF cannot block the rest. Tests and the backfill may call `extractCvText` directly. Reading the file is pure code in `modules/candidate/cv-text/` (`extractCvText`): the type comes from the file's bytes, `layout.ts` puts two-column pages in reading order, `clean.ts` tidies the text, and `quality.ts` marks a scan or an image-only CV as `empty` instead of storing rubbish. `normalize-search.ts` rewrites terms Postgres cannot keep (`C++`, `.NET`, `Node.js`) and must be applied to a search query as well as to the stored text. Raise `EXTRACTOR_VERSION` when a change would give a different result for the same file, then run the backfill. A result is only saved onto the row for the same `resume_key`, so a job for a replaced CV cannot overwrite the new one. **Search**: the candidate list's `search` matches name or email, or the CV (`cvMatches` in `modules/candidate/cv-text.service.ts`, using `websearch_to_tsquery`, so quotes, `OR` and `-word` work). With a search and no score sort, results are ordered name matches first, then by CV rank. Each row on the page gets a `cvSnippet` with matches between `[[` and `]]`: plain marks, not HTML, because CV text is untrusted, and the frontend's `splitSnippet` renders them as text. `GET /candidates/:id/cv-text` returns the text under the same access rule as opening the candidate. **Details read from the text** (`cv-text/profile.ts`, by rules, no AI): the CV split into sections by its headings, approximate years of experience from the date ranges in the Experience section (overlapping jobs counted once), the highest education level, and contacts. The years and the level are estimates: null means "could not be worked out" and is shown as "Not found", never as zero; they are always worded as estimates in the UI and are never part of the candidate score. Job titles, employer names and a skills list are deliberately not extracted, because no rule gets them right across layouts and sectors. The `minExperience` list filter leaves out candidates whose years are unknown. After changing these rules run the backfill with `--reparse`; `EXTRACTOR_VERSION` is only for changes to how the file itself is read.
- **CV files** are in a bucket with no public access (`R2_PRIVATE_BUCKET_NAME`); only logos are in the public one (`R2_BUCKET_NAME`). The database keeps the file's key (`candidates.resume_key`, `resumes/<uuid>.pdf`), never a URL, and API responses say only `hasResume`. The one way a CV leaves storage is `GET /candidates/:id/resume`, which checks access and then sends the bytes itself: do not add presigned or public links. `shared/services/r2.service.ts` is the only code that talks to storage. An applicant never names a file: `POST /public/upload/resume` records the upload in `resume_uploads` and returns its id, and apply claims that id inside its transaction (`modules/upload/resume-upload.service.ts`), so an id works once and for one hour. Uploads that are never used are deleted, with their files, by the periodic check in `server.ts`. **Deleting a candidate erases their CV file**: every place that deletes `candidates` rows (`candidateService.delete`, `deleteManyByFilters`, and both job deletes in `job.service.ts`) returns the keys and calls `requestResumeDeletion` (`queues/resume-delete/queue.ts`) after the delete commits; any new code that deletes candidates must do the same. Every table with a `candidate_id` cascades. Do not log candidate names or email addresses, only ids: logs outlive a deletion. **Bulk delete** (`DELETE /candidates/bulk`) must say exactly what it deletes: `{ candidateIds }` (at most 200), or `{ jobId, expectedCount, ...filters }` for one job, where nothing is deleted unless exactly `expectedCount` candidates match. Never add a form that works without a job or without ids.
- **AI CV analysis is optional and off by default.** It sends CVs to Google Gemini, so it runs only when the `app_settings.ai_cv_analysis_enabled` switch is on (Settings → General) **and** `GEMINI_API_KEY` is set; `modules/settings/ai-settings.service.ts` (`isCvAnalysisActive`) is the single check. `requestCvAnalysis` in `queues/cv-analysis/queue.ts` is the only way a CV is queued and it enforces that check, and the worker checks again before sending. The Gemini client is created lazily so the server starts without a key. The analysis produces notes only (summary, strengths, gaps, matched/missing skills): there is deliberately no AI score or verdict, and it is never part of the candidate score. While it is off the API returns `cvAnalysis: null` and the candidate page hides the "AI analysis" tab; saved analyses are kept.

### Database

- PostgreSQL via **Drizzle ORM**. Schema files live in `backend/src/db/schema/` (one file per domain + `relations.ts`).
- DB connection: `backend/src/db/index.ts` — pg Pool with Neon scale-to-zero handling (production uses Neon; local dev can point `DATABASE_URL` at any Postgres, including the local Docker container).
- When changing the schema: run `pnpm drizzle-kit generate` in `backend/`, then **commit the generated `drizzle/*.sql` files**.
- The seed (`backend/src/db/seed.ts`) creates 5 default pipeline stages (Applied, Screening, Interviewed, Offer, Rejected) - required for the app to function.
- **Local Postgres + Redis**: `docker-compose.yml` at the repo root runs both as containers (`openats`/`openats`/`openats` for user/password/db on Postgres; Redis with no auth). Not required — Neon/hosted Redis work too — but this is the fastest path for local dev. See `CONTRIBUTING.md` for the full setup flow.

### Frontend

- **Next.js** with `force-dynamic` on the root layout (`frontend/app/layout.tsx`).
- **Session and API token**: `frontend/lib/auth/session.ts` (`getSession`, `getApiToken`, `requireRole`) is the only place server code reads the Better Auth session or issues the JWT sent to Express. `frontend/proxy.ts` only checks that a session cookie exists; the dashboard layout does the real check with `getSession()`.
- **Auth hardening** lives in `frontend/lib/auth/options.ts`: rate limits stored in `auth_rate_limits` (so they hold across server instances), `trustedOrigins` limited to `BETTER_AUTH_URL`, 7-day sessions, secure cookies in production. `frontend/instrumentation.ts` runs `lib/env.ts` at server start and exits when `DATABASE_URL`, `BETTER_AUTH_SECRET` (32+ characters) or `BETTER_AUTH_URL` is missing.
- **User management** (`frontend/app/api/users/*`) goes through the Better Auth admin API (`auth.api.createUser`, `adminUpdateUser`, `setRole`, `banUser`, `setUserPassword`), always with the caller's headers so Better Auth checks the role itself. Users are never hard-deleted: deactivating bans the user and then soft-deletes through Express. `frontend/lib/users/rules.ts` holds the input parsing and the guards that stop the last super admin being removed.
- Heavy components are code-split with `ssr: false` via `frontend/components/dynamic-imports.tsx`.
- **Tailwind v4** — CSS-first config (`@tailwindcss/postcss`), no `tailwind.config.ts`. Theme defined via `@theme` in CSS globals.
- **shadcn/ui** with `base-vega` style. Icon library is **hugeicons** (not lucide or heroicons).
- Path alias: `@/*` → `./*` (configured in both `tsconfig.json` and Next.js config).
- **Server-side data fetching**: `serverFetch` in `frontend/lib/server-fetch.ts`, which attaches the token from `getApiToken()`.
- **`frontend/lib/auth/`** holds sign-in and sessions: `server.ts` (the Better Auth instance, also the CLI's `--config`), `options.ts`, `client.ts` (browser), `permissions.ts`, `session.ts`, `errors.ts` (messages and password rules), `password-emails.ts`, and `db.ts` (the pool, used only by auth). **`frontend/lib/users/`** holds user management: `admin.ts` and `rules.ts` for the `/api/users` routes, `client.ts` for the browser.
- **Client-side data fetching**: `useApi` hook + React Query hooks in `frontend/hooks/queries/`.
- **Roles in the UI**: read them with `useRole()` (`frontend/hooks/use-role.ts`: `isManager`, `isSuperAdmin`, `isInterviewer`), never by comparing role strings, and guard a whole page with `<RoleGuard allow="manager" | "super_admin" redirectTo=…>` (`components/guards/role-guard.tsx`). This only hides UI; the API enforces every rule itself. Server data is shared through React Query, not React context.
- **Component placement convention** (App Router private folders, which Next.js leaves out of routing):
  - Code used by one route lives beside it in `_components/`, `_lib/` and `_hooks/`. Every private folder inside `app/` starts with an underscore; never add a plain `lib/` or `hooks/` there. Nest further for large features (e.g. `templates/_components/template-form/email-builder/`).
  - A route never imports from another route's private folders, only from its own and its ancestors'. When a second route needs something, move it to the nearest common parent: `(dashboard)/_components` / `(dashboard)/_lib` for dashboard pages (the interview scheduler lives there), `assessments/_components/builder` for the assessment builder shared by `new` and `[id]`. Tests may import any of them.
  - Code used across the whole app goes in the top-level `frontend/components/` (shadcn primitives in `components/ui`, shared `components/table`), `frontend/lib/`, `frontend/hooks/` and `frontend/hooks/queries/`. These never import from `app/`.
  - A component loaded with `next/dynamic` is declared in the file that uses it. `components/dynamic-imports.tsx` is only for shared ones (the drag and drop provider).
  - File names are kebab-case (`job-header.tsx`), exports are named.

## Testing

See `docs/docs/developer/testing.md` for the full guide. In short:

- **Unit + integration tests** use Vitest and live in `backend/tests/` (`unit/`, `integration/`), excluded from `tsconfig.json` compilation. Config is `backend/vitest.config.mts` (`.mts` because the backend is a CommonJS package).
- **End-to-end tests** use Playwright and live in `e2e/` at the repo root, because they span both packages. Config is `playwright.config.ts`, and `tsconfig.json` at the root covers them.
- **Integration tests hit a real database**: a separate Postgres on port **5433** (`postgres-test` in `docker-compose.test.yml`, started with `docker compose -f docker-compose.test.yml up -d`). Its data does not survive a stop, so run the migrations against it again after starting it, never the dev database on 5432. `backend/tests/setup.ts` loads `backend/.env.test` with `override: true` to enforce this.
- `backend/.env.test` is committed on purpose. It holds no secrets, only dummy values, so that tests pass on pull requests from forks (GitHub never gives secrets to those).
- E2E tests also use the 5433 database, via `webServer.env` in `playwright.config.ts`. `reuseExistingServer` is `false` so an already-running `make dev` cannot be adopted, which would silently point tests at the dev database. **Stop `make dev` before running E2E.**
- Commands: `pnpm test` (backend then frontend unit tests), `pnpm test:frontend`, `pnpm test:coverage` (v8 coverage on the backend), `pnpm test:e2e` (Playwright), `pnpm exec tsc --noEmit` (type-check the E2E specs, which Playwright does not do).
- CI runs tests, type-check, and the backend build on every pull request (`.github/workflows/ci.yml`). It deliberately uses no secrets.
- **Frontend tests** use a separate Vitest install in `frontend/` with jsdom and Testing Library, in `frontend/tests/`. They cover pure helpers and rendered components; there is no network or router mocking set up yet.

## Environment Variables

Two separate `.env` files are required (copy from `.env.example` in each directory):

- `backend/.env` — `DATABASE_URL`, `REDIS_URL`, `ENCRYPTION_KEY` (32 bytes in base64, checked at start), `TRUST_PROXY` (optional), `R2_*`, `RESEND_*`, `AUTH_JWKS_URL`, `AUTH_ISSUER`, `GEMINI_API_KEY` (optional), `GOOGLE_OAUTH_CLIENT_ID` / `GOOGLE_OAUTH_CLIENT_SECRET` / `GOOGLE_OAUTH_REDIRECT_URI` (optional)
- `frontend/.env` — `OPENATS_API_URL`, `NEXT_PUBLIC_API_URL`, `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `RESEND_API_KEY` / `RESEND_FROM_EMAIL` (optional; invite and reset emails are sent from the Next.js server by `frontend/lib/auth/password-emails.ts`)

## CI/CD

- `.github/workflows/ci.yml` runs on every pull request: backend lint, type-check, unit and integration tests, the backend build, the frontend tests, and a check that Better Auth's tables match the migrations. It uses no secrets.
- `.github/workflows/release.yml` cuts a release and generates its notes from PR titles and labels (`.github/release.yml`). PRs are squash-merged, so the PR title is the commit on `main`.
- There is no deploy workflow; deployment is done by hand.
- Both packages have ESLint. Only the backend's is enforced in CI, because the frontend still has existing lint errors.
